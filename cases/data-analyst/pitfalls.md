# 数据口径陷阱手册

> 14 个真实踩过的坑。每一个都曾产出过"看起来很对"的错误结论，并且至少有一个进了正式报告。
> 按"最容易骗过 AI 和人"排序——越靠前的越隐蔽。

> ⚠️ 本文数字均为**示意值**，用于说明误差的量级关系，不是真实业务数据。

**怎么用这份手册：** 它可以直接抄进你的 agent 定义或 code review 清单。
每条的结构是：**现象 → 根因 → 怎么发现的 → 通用规则**。通用规则那行才是能搬走的东西。

## 1. 爬虫不是流量

**现象**
报表说昨日到访 220 台设备，实际真人 8 个。日到访九成以上是噪声。

**根因**
两类东西被当成了用户：

- **服务端渲染产生的一次性身份**：每次爬虫请求都会走一遍"注册游客 → 拉列表"的自动接口链路，每次生成一个新设备号。
- **自动接口 ≠ 主动行为**：拉推荐流、拉频道列表、拉角色详情——这些接口爬虫也会触发，出现它们不能证明有人在操作。

**怎么发现的**
用真人一定会做的动作（发消息、点登录）反查：220 台设备里只有个位数触发过任何主动行为。

**解法：双判据剔除**

```
设备级判据：
  · 一次性身份前缀（服务端渲染生成的 id 有固定前缀）—— 示意占比八成以上
  · Headless 浏览器 UA
  · 开发环境前缀 + 已知测试设备黑名单

身份级判据：
  · 把接口分成两类：
      「自动接口」——注册游客/鉴权/取随机数/拉推荐流/拉频道列表/拉角色故事/搜索
      「主动接口」——登录/发消息/进入对话/查看我的资料
  · 窗口内只触发过自动接口的身份 = 爬虫
```

两个判据要**交叉验证**：如果设备级判出八成是爬虫、身份级只判出个位数百分比，说明有一边写错了。

> **通用规则：** 定义"活跃"时，先定义"哪些行为不算活跃"。默认全算，等于默认相信爬虫。

## 2. 占位 id：身份还没生成时的行为

**现象**
报表显示"新用户登录数"每天恒为 0。结论差点写成"新用户完全不注册，登录墙是死路"。

**根因**
登录事件是在**登录成功之前**上报的——此时客户端还没拿到真实账号 id，字段里填的是一个客户端生成的一次性占位值（实现上是负的毫秒时间戳，每个事件一个新的，不复用、不跨事件稳定）。

分析层的 uid 表达式按设计把 `0` / `-1` / 负数归为"匿名"，所以 `COUNT(DISTINCT uid)` 不受影响——**但按 uid 做 JOIN 会全部落空**，得到一个精确的 0。

**怎么发现的**
换成按设备号统计，同样的窗口里登录事件不是 0，而是每天几次到十几次。

> **通用规则：** 一个字段有值 ≠ 这个值可用于关联。
> 身份未确定时发生的行为（登录、注册、首次访问），一律按**设备号**归因，不按账号 id。
> 判断某字段能不能 join，看它在**事件发生的那一刻**是否已经确定。

## 3. 设备 vs 账号：别用 uid 当人头

**现象**
按账号 id 首次出现算"新客"，得到每日 50~130；按设备首现算，同期是 20~30。差 2-3 倍，而且和公司 BI 的口径对不上。

**根因**
两个叠加因素：

1. **数仓有起点**（见[陷阱 14](#14-左删失与数据起点)）：数仓只保留了某个日期之后的数据，之前就存在、中间休眠、最近回流的老用户，会被"首次出现账号 id"误判成新客。
2. **一机多号**：一台设备上游客态反复登录、多账号切换，会产生多个"新账号"，但只有一台新设备。

设备首现同时避开这两个坑，≈ 真实新装机/新访客。

> **通用规则：** "新用户"的权威口径是**新设备**，不是新账号。
> 账号口径只用于跨端身份追踪这类必须靠账号的场景——而且此时只看**比例**，不看绝对值。

## 4. 任意事件首现 ≠ 新客

**现象**
修好[陷阱 3](#3-设备-vs-账号别用-uid-当人头) 之后，设备口径新客仍然比权威 BI 数字高 0~7 个/天，稳定偏高。

**根因**
"设备首现"用的是**任意事件**的最早出现时间。而有些事件发生在用户真正打开产品之前或之外——推送回执、后台静默上报、预热请求。这些会把首现日提前，制造出"更早的新客"。

**解法**
首现要用**平台首开信号**，不是任意事件：

```
App 端：首次 app_open           = 公司 BI 的新增设备口径
Web 端：首次 web_session_start  = 与 app_open 对称的"首次真实会话"
```

改完之后逐日对得上 BI 曲线。

⚠️ 附带一个坑：如果这个"首开事件"本身是某天才上线的埋点，上线前的新客会全部记 0，随窗口滚动逐渐消失。要在报表里标注埋点上线日。

> **通用规则：** cohort 的首现判据必须是**能代表"用户真的开始使用"的单一信号**，不是"任意一条数据"。

## 5. 事件名不是你在代码里写的那个

**现象**
查"用户发消息"事件，返回 0 行。据此写下结论："前端没有这个埋点，需要补。"

**根因**
数仓的事件落库名是网关拼接出来的：`落库名 = 对象类型 + "_" + 动作名`。代码里写的是 `chat_round_start`（动作名），落库之后叫 `chat_chat_round_start`（对象 `chat` + 动作 `chat_round_start`）。

按代码里的名字精确匹配，查到 0。而 0 被当成了"不存在"。

**怎么发现的**
被追问"你确定吗"之后，改成先拉事件名清单：

```sql
SELECT `@event_name`, COUNT(*) FROM t_event
WHERE `@dt` >= '...' AND `@event_name` LIKE '%round%'
GROUP BY 1 ORDER BY 2 DESC
```

一眼看到真名。

> **通用规则：** 查"某事件是否存在"，先用模糊匹配**拉清单**，再精确统计。
> 精确匹配返回 0，只能证明"这个名字没有数据"，不能证明"这个行为没有埋点"。

## 6. 缺失类结论必须双向验证

**现象**
发现 40 台设备有服务端对话记录、却没有任何客户端埋点事件。结论："这批是绕过网页直连 API 的客户端。"

听起来很合理，还带着数字。**是错的。**

**根因**
只做了**单向验证**：证明了"这些设备 id 下没有客户端事件"。没有验证"客户端事件是不是挂在**别的 id** 上"。

反向一查：全库里存在 52 台"孤儿设备"——有客户端聊天事件、没有服务端对话记录。用账号 id 和时间去配对，两批设备一一对上：**是同一批用户，同一次对话，落在了两个设备号上**（见[陷阱 7](#7-身份分裂两套设备-id)）。

再做一次总量对账：客户端聊天事件总数与服务端对话事件总数是 1:1 的。**一侧"缺失"而总量对齐，几乎必然是关联键断裂，不是数据缺失。**

> **通用规则：** 任何"X 缺少 A"的结论，需要三重证据：
> 1. 正向：X 下确实没有 A
> 2. 反向：全库中承载 A 的孤儿实体，用另一个键（账号/时间/量级）与 X 配不上
> 3. 对账：A 的两侧总量不对齐
>
> 配对成功 = 关联键断裂，**不是**缺失。

## 7. 身份分裂：两套设备 id

**现象**
[陷阱 6](#6-缺失类结论必须双向验证) 的根因。同一个用户在数仓里有两个设备号，服务端事件挂一个、客户端埋点挂另一个。分端统计（PC / 移动端）因此失真。

**根因**
系统里存在两个独立铸造设备 id 的地方：

```
浏览器侧：前端 JS 生成，存 localStorage      → 客户端埋点带这个
服务端侧：BFF 首次渲染时生成，写 cookie      → 服务端事件带这个
```

两者只在部分登录路径上对齐。游客优先的访问路径下，一个人天然有两个 id。

**影响面要分清**（这一步很关键，避免过度修复）：

| 指标类型 | 是否受影响 |
|---|---|
| 账号口径指标（对话人数、留存、新增） | ❌ 不受影响——同一个账号 |
| 设备口径归因（PC/H5 分端、设备留存） | ✅ 受影响 |

**临时解法**（治标）：对分裂设备，用该账号在浏览器侧事件的**多数票**回补归端；回补后仍无法归因的进一个单独的监控桶，作为分裂程度的度量——修好之后它应该趋近于零。

**根治**（治本）：设备 id 单一来源，服务端和客户端共用同一个铸造点。

> **通用规则：** 系统里凡是有两个地方能生成同一类标识符，就一定会分裂。
> 上线前先问："这个 id 有几个铸造点？"
> 修不了的时候，至少给失真程度建一个**可观测的监控桶**，别让它悄悄污染报表。

## 8. 服务端事件是全平台共用的

**现象**
统计 Web 端对话用户的回访率，得到 45%。实际约 5%。虚高十倍。

**根因**
用的对话事件是**服务端记录**的，App 和 Web 共用同一个事件名。示意量级：同一时间窗内 App 侧十万量级行、Web 侧千量级行。查询没加平台过滤，把 App 用户全拉进了 Web 的 cohort——分母里塞满了活跃度高得多的 App 用户。

**解法**
所有服务端事件的查询，强制带平台维度过滤。并且在埋点注册表里给这类事件打一个显眼的警告标记：

```
⚠️ 口径坑：这是全平台服务端事件，任何单端归因必须带 chan 过滤，
   漏掉会让 cohort 虚胖数十倍。
```

> **通用规则：** 区分"客户端埋点"和"服务端事件"。
> 前者天然带平台上下文，后者天然不带——**它记录的是业务发生了，不是谁在哪发生的。**

## 9. 时区：数仓存的和业务要的不是一个时间

**现象**
报表的分天数字和分析平台的日本时区数字总是对不上，差一个"边缘时段"的量。

**根因**
事件时间戳字段存的是 UTC+8，业务口径要 UTC+9。差 1 小时——听起来很小，但每天有 1 小时的事件被分到了错误的自然日。对日活个位数到两位数的产品，这足以改变趋势方向。

**解法**
所有分天/窗口逻辑统一加偏移，**两处都要改**：

```sql
-- 分桶（决定这条数据算哪天）
TO_DATE(`@dt` + INTERVAL 1 HOUR)

-- 窗口（决定查哪些数据）
(`@dt` + INTERVAL 1 HOUR) >= '2026-07-01 00:00:00'
  AND (`@dt` + INTERVAL 1 HOUR) <  '2026-07-02 00:00:00'
```

验证方式：拿一个单一事件的逐日设备数，和分析平台的日本时区数字逐日对——连续对上 6 天才算通过。

> **通用规则：** 时区修复必须同时改**分桶**和**窗口**。只改显示的日期标签是自欺欺人。
> 另外：不要在脚本里用运行机器的本地日期。默认日期显式指定业务时区。

## 10. 聚合方式：pooled vs 日率平均

**现象**
同一批数据、同一个窗口，两份报表算出 52% 和 47%。都没写错 SQL。

**根因**
两种数学上就不相等的聚合方式：

```
日率简单平均 =  (r₁ + r₂ + ... + r₇) / 7          ← 每天等权重
合并分子分母 =  (Σ分子) / (Σ分母)                  ← 每个人等权重
```

小样本下差异巨大：某天分母只有 3 人、留存 2 人 = 66.7%，另一天分母 20 人、留存 8 人 = 40%。简单平均给了那 3 个人和那 20 个人**同样的权重**。

**解法**
比率类指标统一用 **pooled（合并分子分母）**，并写进契约层：

```python
class Agg(Enum):
    DISTINCT_WINDOW = "distinct_window"   # 窗口内去重（周聚合 ≠ 日求和）
    SUM             = "sum"               # 事件计数，可跨日求和
    POOLED          = "pooled"            # 比率：合并分子分母，禁日率平均
    MEDIAN          = "median"
```

顺带一个相关坑：**周窗口重叠**。本周窗口 7 天、上周窗口 8 天且共用一天，环比时那一天被算了两次。窗口定义要写死"本周/上周各 N 天且不重叠"。

> **通用规则：** 每个指标必须声明**聚合规则**，和它的定义写在一起。
> "日指标怎么变成周指标"不是显然的，去重指标不能求和，比率指标不能平均。

## 11. 未成熟窗口：今天的次留是假的

**现象**
同一份次留报表，早上跑和晚上跑数字不一样，而且**系统性偏低**。

**根因**
报告日的"次日留存"需要看第二天的完整数据——而第二天正在进行中。跑得越早，第二天累积的数据越少，留存率越低。这个值每跑一次都不同。

更糟的是它被算进了周均值里，把整周的数字往下拽。

**解法**

```
只计算「成熟日」：D1 需要 D+1 天完整，D7 需要 D+7 天完整
未成熟的格子显示 "—"，不显示 "0%"
```

显示 `0%` 是第二个陷阱——读者会以为"这天留存真的是 0"，而不是"这天还没到能算的时候"。

> **通用规则：** 任何跨天指标都有成熟期。
> 未成熟 ≠ 零。显示 `—`，并且不计入任何均值。

## 12. 窗口边界 off-by-one

**现象**
互动次留从 41% 变成 44%。没人改口径，数字自己涨了 3 个点。

**根因**
逐日循环里的排除条件用**窗口端点**做代理判断：

```python
# 错误写法
for day in days:
    nxt = day + 1
    if str(nxt) == str(end_excl):   # 「最后一天没有明天的数据」
        continue
```

写的时候脑子里想的是"最后一天没有次日数据"。但查询窗口后来已经多拉了两天来覆盖 D+1——数据其实是有的。结果最后一天被无端跳过了，而它恰好是低于均值的一天，一跳过均值就虚高。

**正确写法**

```python
for day in days:
    nxt = day + 1
    if nxt not in uids_by_day:      # 直接检查数据是否真的存在
        continue
```

> **通用规则：** 排除条件要基于**数据是否真的可用**，不要用窗口端点做代理。
> 查询窗口和循环边界必须同步审查——改了一个，必须去看另一个。
> 新写的逐日聚合，验证时逐日打印中间值（每日分子/分母/比率），确认首尾两天都在。

## 13. 混粒度比率

**现象**
报表上有一行"激活转化率 = 深度用户数 ÷ 到访设备数"。分子是账号，分母是设备。这个百分比是什么意思？没人答得上来。

**根因**
分子分母粒度不同，比值没有可解释的语义。它既不是"多少人转化了"（分母不是人），也不是"多少设备转化了"（分子不是设备）。它只能用来看**趋势方向**，不能当 KPI，更不能定目标。

**解法**
在契约层把粒度写死，构造时校验：

```python
class Grain(Enum):
    DEVICE = "device"; UID = "uid"; WEB_SESSION = "web_session"
    CHAT_SESSION = "chat_session"; EVENT = "event_count"

@dataclass(frozen=True)
class Ratio:
    numerator: str; denominator: str; kind: RatioKind   # KPI | DIAGNOSTIC

    def validate(self):
        if METRICS[self.numerator].grain != METRICS[self.denominator].grain \
           and self.kind != RatioKind.DIAGNOSTIC:
            raise ValueError(f"{self.ratio_id} 混了粒度：标 DIAGNOSTIC 或修正")

for r in RATIOS.values():
    r.validate()      # import 时就炸，不等到出报表
```

混粒度不是绝对禁止——有些诊断信号确实只能这么算。但必须**显式标记为 DIAGNOSTIC**，且报表头条不允许用诊断口径。

> **通用规则：** 比率的两端必须同粒度。
> 做不到就显式降级为"诊断信号"，并且禁止它出现在结论层。

## 14. 左删失与数据起点

**现象**
用全史"首次出现"判断新客，结果某些月份新客数异常地高。

**根因**
数仓的数据起点晚于产品上线时间。起点之前就存在的老用户，一旦在窗口内回流，就会被判成"首次出现"=新客。

这个偏差**无法靠拉长回溯窗口修复**——数据本身被截断了。

**解法**
两条一起用：

1. 用设备口径 + 平台首开信号（见[陷阱 3](#3-设备-vs-账号别用-uid-当人头)、[4](#4-任意事件首现--新客)），把偏差压到最小
2. 在文档里显式写下数据起点日期，并在所有 cohort 类分析里注明"左删失，起点前的老用户可能被计入新客"

同一类问题还有一个变体：**埋点污染期**。埋点体系上线初期（字段缺失、重复上报、口径未定）的数据不可用。解法是设一个**基线日期（FLOOR）**：

```python
FLOOR = "2026-06-12 00:00:00"      # 埋点 v0.2 上线日
start = max(requested_start, FLOOR)
# 若被 clamp，报表标注"窗口不足 N 天"
```

> **通用规则：** 明确写下你的数据有效起点，并在所有跨期分析里 clamp 到它。
> 留存/cohort 分析要求窗口 ≥ 关注周期的 2 倍，否则左删失会系统性地扭曲结论。
