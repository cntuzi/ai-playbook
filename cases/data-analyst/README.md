# 构建一个数据分析师

> 一个能自己查数仓、套对口径、给出可信结论的数据分析 agent。
> 以及一个反直觉的结论：**这件事 90% 的工作不在 prompt 里。**

**技术栈：** Apache Doris + Python + Claude Code subagent + 埋点注册表 + 指标 SSOT + 定时推送

**配套文档：**

- [从零构建教程](./tutorial.md) —— 七步，从埋点注册表到可对话 agent，含代码
- [数据口径陷阱手册](./pitfalls.md) —— 14 个真实踩过的坑，每个都曾产出过"看起来很对"的错误结论

> ⚠️ 本文所有业务数字均为**示意值**，用于说明口径差异的量级关系，不是真实业务数据。
> 工程结构（分层、机制、文件职责）是真实的。

---

## 一句话结论

数据分析师 agent 不是"一个会写 SQL 的 LLM"。它是四层东西的叠加：

```
事实源（埋点注册表）→ 指标 SSOT（唯一实现）→ 口径纪律（可自检清单）→ agent
```

**缺任何一层，LLM 都会一本正经地给你错数字。** 而且因为它写 SQL 很快、叙事很流畅，错误会以更高的速度、更强的说服力扩散。

我做了三代才明白这件事。这篇记录三代分别错在哪、最后的架构长什么样、以及哪些经验能搬走。

---

## 三代演进：每一代都能跑，每一代都错

### 第一代：能查数（"给我建个数据看板"）

做法很自然：写 Python 脚本连数仓，一个报表一个脚本。日报、周报、双周报、月报、全量报告，外加一个 `queries/` 目录放 SQL 文件、一个 manifest 描述哪个报表跑哪些 SQL。

跑起来了。第二天就出问题：

```
报表说：昨日到访 220 台设备
实际：真人 8 个
```

**根因：没有事实源，只有数据源。** 数仓里躺着事件，但没人定义过"什么算一次到访"。爬虫触发的服务端接口日志、SSR 渲染产生的一次性设备号、开发环境的测试流量、内部账号——全都算进去了。示意量级：某天 220 台"到访设备"里 210 台是爬虫。

第一代的产出不是错在 SQL，是错在**没有人写下过口径**。LLM 帮我很快地写出了语法正确、语义无意义的查询。

### 第二代：能写报告（"再加个分析师 agent"）

补了两样东西：

1. **埋点注册表**（`EVENTS.md`）：每个事件的落库名、触发时机、字段字典、版本、状态。爬虫判别规则也写进去。
2. **可对话的分析 agent**：随口问一个问题（"详情页到开聊为什么卡住"），它自己写 SQL 下钻、给归因结论。

同时把报表体系正规化：北极星指标、滚动 7 日窗口、逐日趋势、留存 cohort、漏斗分维度。

这一代看起来很像样了。日报每天准时推送，agent 能回答问题。然后**两份报表打起来了**：

| 指标（同一周窗口） | 周报 | 每日看板 |
|---|---|---|
| 互动次留 | 52% | 47% |
| 活跃 UID | 80 | 240 |
| 新增 UID | 45 | 205 |

*（示意值，量级关系为真）*

同一个指标名，同一个时间窗，两个数。哪个对？

### 第三代：找到真正的病（这才是转折点）

我没有直接改数字，先做了根因分析。查下来，同一个"对话次留"在两份脚本里存在：

- **2 套事件集合**（一边只认服务端轮次事件，一边认 3 个事件的并集）
- **2 种聚合方式**（逐日算率后简单平均 vs 合并分子分母）
- **2 种窗口天数**（7 天 vs 8 天，且和上周窗口重叠了一天）
- **2 种过滤规则**（一边有爬虫过滤，一边裸奔）

2×2×2×2 = 16 种可能的"次留"。两份报表各自随机取了一种。

**这不是 bug，是结构决定的必然。** 当时的共享库只共享了"怎么连数据库"（`run_sql`）和几个零散常量，没有共享**指标定义**。于是每个报表脚本都要自己写一遍"什么是次留"，而每个人（包括每一次 AI 会话）对口径的理解都会漂一点。

关键认识：

> 修一次口径需要在 6 个地方手工同步，漏一处就是新的不一致。
> 在这个结构下，**AI 加速的是"错得更快"**——它能在 30 秒内写出第 7 个平行定义。

## 最终架构：指标只允许存在一份代码

```
┌──────────────────────────────────────────────────────────────┐
│  L0  事实常量                              facts.py          │
│  UID 表达式 / 内部账号名单 / 爬虫接口集合 / 设备过滤 CTE     │
│  时区规则 / 数据基线日期                                     │
│  ★ 唯一允许声明这些字面量的地方                              │
└───────────────────────────┬──────────────────────────────────┘
                            │ import
┌───────────────────────────▼──────────────────────────────────┐
│  L1  指标定义层                            metrics.py        │
│  每个共享指标一个函数：输入=时间窗，输出=数值/逐日序列       │
│  函数体内是该指标的【唯一 SQL】                              │
│  docstring 写口径一句话 + 生效日期                           │
└───────────────────────────┬──────────────────────────────────┘
                            │ 注册 / 校验
┌───────────────────────────▼──────────────────────────────────┐
│  L2  指标契约                       metric_contract.py       │
│  指标 → 粒度(device/uid/session/event) / 聚合规则(pooled/sum)│
│         / 成熟度规则 / 实现函数名                            │
│  比率两端粒度不一致 → 构造时直接抛异常                       │
└───────────────────────────┬──────────────────────────────────┘
                            │ 调用
┌───────────────────────────▼──────────────────────────────────┐
│  L3  报表层                    4 个报表脚本（只做排版）      │
│  调 L1 取数 → 排版 → 对比展示                                │
│  ★ 红线：报表脚本内禁止出现指标 SQL                          │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  L4  消费层                                                  │
│  定时日报/周报（截图推送）  +  可对话 agent（随问随答归因）  │
└──────────────────────────────────────────────────────────────┘
```

配套三份文档，**互相引用、不互相复制**：

| 文档 | 职责 | 回答什么问题 |
|---|---|---|
| `EVENTS.md` | 埋点注册表 | 这个行为有埋点吗？落库叫什么名？带哪些字段？ |
| `DATA_SEMANTICS.md` | 口径语义 + 生效史 | "到访"到底是什么？什么时候改的口径？ |
| `REPORT_SPEC.md` | 业务含义 + 北极星 + 维度树 | 为什么要看这个指标？它属于哪块业务？ |

"不互相复制"是硬约束。复制 = 三份会各自漂移 = 又回到第一代。

## 让架构自己守住：三道闸

分层只是"应该这样做"。没有强制机制的规范，三周后就烂了。所以配了一个自检脚本（`verify_metrics.py`），跑报表前置执行，任一失败就非零退出——**宁可缺报，不出错报**。

```
闸 1  静态红线
      正则扫描报表脚本：出现 COUNT(DISTINCT ...) AS <共享指标别名> 即报错
      → 从机制上杜绝"再写一个平行定义"
      → 专项下钻分析用行内 # ssot-allow 显式豁免（豁免必须留痕）

闸 2  契约完整性
      L2 里注册的每个共享指标，其声明的实现函数必须真实存在于 L1
      → 防止契约和实现脱钩（改了代码忘了改契约）

闸 3  数据不变式（--live，查库）
      对昨日数据断言结构性事实：
        · 对话 UID ⊆ 活跃 UID
        · 留存分子 ≤ 分母
        · 到访设备 > 0（=0 说明埋点断流或口径破了）
        · 分端拆分之和 = 总量（对账封闭）
      → 这些断言不依赖具体数值，量级涨十倍也不用改
```

第三道闸最值钱。它不检查"数字对不对"（没有基准可对），它检查**结构不变式**——那些无论业务怎么变都必须成立的关系。口径一旦破了，这些关系会先崩。

配套还有一条变更流程：

> **改口径 = 改 L1 一个函数 + 改 L2 一行契约 + 改 `DATA_SEMANTICS` 一行生效日期。**
> 这三处以外出现的口径变更，即违规。

生效日期那一行不是形式主义。口径改了之后，新旧数字不可直接环比——报表 footer 必须标生效日，否则半个月后有人拿改口径前后的数字做趋势对比，又是一次错误结论。

## Agent 怎么设计：指向事实源，不复制事实

有了前面四层，agent 的定义反而变得很短。核心是四件事：

### 1. 定位要划死：产出数据，不做决策

```
@data-analyst  →  产出原始数据 + 口径严谨的归因，不做产品决策
@strategist    →  消费报告做战略判断，不写 SQL
```

分开是有代价的（多一次对话），但值得：一个既查数又拍板的 agent，会不自觉地**为自己的结论找数据**。明确写进 agent 定义的一条禁令：

> ❌ 不为"证明某个预设结论"找数据。应该是"分析后得结论"，不是"找证据撑结论"。

### 2. 必读文件：指向，不复制

agent 的 prompt 里**不写指标定义**，只写"指标定义在 `REPORT_SPEC.md` §1，去读它"。

这条很反直觉——把定义抄进 prompt 明明能省一次文件读取。但抄进去就等于第 N+1 份平行定义，源文件改了 prompt 不会跟着改，几周后 agent 会用一套没人维护的旧口径给你结论。**prompt 是会过期的缓存。**

### 3. 口径纪律：一份查询前的自检清单

这是 agent 定义里最长的一节，也是最有价值的一节。八条，写 SQL 前逐条对照：

```
1. 时区     数仓存 +8，业务口径 +9 → 所有分天/窗口逻辑加 1 小时
2. 基线     埋点污染期之前的数据不可比，窗口起点 clamp 到基线日
3. 爬虫     双判据剔除：设备级（一次性 id 前缀 / Headless UA / 测试黑名单）
                       + 身份级（窗口内只触发自动接口的 uid）
4. 内部     内部账号全史回溯剔除
5. 占位 id  0 / -1 / 负数 uid 视为匿名，身份兜底到设备号
6. 方言     保留字别名加反引号、分位数函数写法、时间加减语法
7. 排序     逐日/时序表一律倒序（最新在顶）
8. 粒度     device / uid / session / event 不同粒度不能直接做比率
```

第 8 条由 L2 契约层在代码里强制；其余七条靠 agent 自检。人也用同一份清单——**人和 agent 用同一套纪律，才不会互相怀疑对方的数字。**

### 4. 输出格式：强制五段

```
1. 结论先行     一句话回答问题
2. 证据表       支撑结论的数字（分维度/分时序，时序倒序）
3. 口径声明     用了哪个窗口 / 基线 / 时区 / 剔除规则
4. 弱信号标注   小样本标"样本小看方向"，不夸大
5. 数据诚实     断库说断库、跌了说跌了、异常主动标
```

第 3 段是防伪的关键。任何一个数字，配上它的口径声明，读者才能判断该不该信；没有口径声明的数字，无论多精确都是**装饰**。

## AI 在这件事上帮了什么倒忙

这个仓库的理念之一是"包含失败经验"。诚实地说，在数据分析这件事上，LLM 的失败模式很有规律：

| 帮上忙 | 帮倒忙 |
|---|---|
| 一次性下钻查询（人写要 20 分钟，它 2 分钟） | **没有事实源时会"合理地"编**：编字段名、编事件名、编不存在的默认值 |
| 口径审计（拿两份报表逐行对差异，机械但要耐心） | **每次会话重新发明口径**：上次说 7 天窗口，这次自己改成 8 天 |
| 把重复劳动固化成脚本 | **对"缺失"类结论过度自信**："查不到 = 不存在"，实际是名字猜错了 |
| 写报告叙事（数字 → 人话） | **叙事能力掩盖数据错误**：错的数字配上流畅的归因，比错的数字本身危险得多 |

最后一行是核心风险。第二代那份日报，读起来非常专业——趋势、归因、行动建议一应俱全。而它的活跃用户数虚高了两倍多。

**结论：LLM 的产出质量 ≈ 你的事实源质量。**
所以"构建一个数据分析师"的工作量分布是：

```
建事实源 + 强制机制  ████████████████████░░  ~90%
写 agent prompt      ██░░░░░░░░░░░░░░░░░░░░  ~10%
```

## 踩坑记录

### 做对了什么

| 决策 | 为什么重要 |
|---|---|
| 先建埋点注册表，再写任何报表 | 事件落库名、字段、版本有唯一事实源；写 SQL 前先查表，不靠猜 |
| 指标下沉到 L1 唯一实现 | 改口径改一处，所有报表自动同步；杜绝"同名不同义" |
| 契约层强制声明粒度 | 混粒度比率在构造时就抛异常，不会流到报表里 |
| 自检脚本前置，失败就不产出 | 宁可缺报不出错报——错报的伤害是长期的（决策基于它） |
| 口径变更要标生效日期 | 明确告诉读者"这里之前的数字不可环比"，防止跨口径趋势对比 |
| agent 指向事实源而非复制定义 | prompt 不会过期；源文档改了 agent 立刻跟上 |
| 结论必须带口径声明 | 让每个数字可被审计，而不是被相信 |

### 做错了什么

| 错误 | 根因 | 修复 |
|---|---|---|
| 5 个报表脚本各写各的指标 SQL | 只共享了连接方式，没共享指标定义 | 建 L1 指标层 + 静态红线禁内联 |
| 同名指标 16 种可能口径 | 没有人写下过"次留"的唯一定义 | 口径标准表 + 生效日期，落进刚性文档 |
| 到访量虚高 20 倍以上 | 没有爬虫判别；服务端接口日志当真人流量 | 双判据剔除（设备级 + 身份级） |
| 把"新客登录"误判成恒 0 | 按 uid 关联登录事件——而登录时 uid 还没生成 | 身份未定的行为一律按设备号归因 |
| 次留率虚高数个百分点 | 逐日循环里用窗口端点做排除条件，漏掉最后一天 | 排除条件基于"数据是否真的存在"，不基于窗口端点 |
| 断言"这批设备没有客户端事件" | 只做了单向验证（该 id 下没有）；没查"事件是否挂在别的 id 上" | 缺失类结论必须双向验证 + 总量对账 |
| 主张"数据量小，日报少做点" | 把"当前量小"当成"少做"的理由 | 体制按目标量级一次建成；趋势用滚动窗口日频看，不靠汇总周期 |

最后一条值得展开。当时的真实情况是日活很小，单日指标抖动剧烈（一个人的进出就是几个百分点）。我的提议是"日报只做哨兵，全量分析挪到周报"。被否掉了，理由是：

> 体制要按**目标量级**建、一次建成不返工。按今天可怜的样本量缩水，量涨上来还得重构。
> 单日抖动大不是"日频不能看趋势"的理由，是"用滚动窗口化解"的理由。
> 低量期正是这套逻辑的**压测期**——现在就全量跑，在日常使用中把口径 bug 压出来。

事实证明是对的。就是在低量期的日常运行中，暴露出了埋点漏报、字段缺失、口径打架这些问题。如果等量起来再建，这些坑会在数据最重要的时候集中爆发。

## 可泛化的设计原则

这七条不限于数据分析，任何"AI 产出需要可信"的系统都适用：

1. **事实源先于自动化。** 没有唯一事实源时，自动化放大的是错误的传播速度。
2. **定义只允许存在一份代码。** 同一个概念出现两次实现，就是两个概念。
3. **规范要有强制机制。** 没有自检闸的规范，寿命大约三周。
4. **断言结构不变式，不断言具体数值。** 前者不随业务变化，后者天天要维护。
5. **指向事实源，不复制事实。** prompt / 文档里的副本是会过期的缓存。
6. **宁可缺产出，不出错产出。** 错的产出会被当成对的用，伤害是长期的。
7. **每个数字都要能被审计。** 结论带口径声明，读者才能判断该不该信。
