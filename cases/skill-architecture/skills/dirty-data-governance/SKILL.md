# 脏数据治理方法论（通用）

> 一句话：**脏数据 = "生成而非对齐"的沉淀。治理 = 建真实源契约 + 一次全量核对，不发现一个清一个。**
> 适用：任何项目。每次总结/复盘/重大产出时把它当默认检查项。
> 权威完整版（含案例/模板/演进）在 MooX Web 项目 `methodology/dirty-data-governance/`（AI Native 方法论库孵化地，团队共享）；本文件是跨项目个人便携版，更新时与权威源同步。

---

## 1. 什么是脏数据（五类）

| 类型 | 定义 | 例子 |
|------|------|------|
| **假 UI / 假字段** | 前端有 UI/字段，真实源（后端）不支撑 | 后端没有的枚举/字段、提交即丢的输入 |
| **字段错配** | 名/枚举值/类型前后端对不上 | 字段名错位、枚举值前后端不一致、类型不符 |
| **术语混乱** | 同一概念多个词混用 | NSFW / R18 / Mature / Adult 指同一分级 |
| **文档/知识库残留** | 旧方案、**被否决策**、过时假设未清 | 已推翻的路线/架构仍残留在规划/文档里 |
| **假功能 / 占位** | 有 UI 入口但走 mock/写死/TODO/不通后端 | mock 数据、写死列表、TODO 未实现 |

---

## 2. 根因（为什么会有脏数据 + 为什么清不干净）

- **产生**：前端/文档凭直觉"生成"，不对齐真实源。字段名自己起、枚举自己编、造真实源没有的概念。
- **清不干净**：只在**症状层**清理（发现一个清一个）。脏数据是**存量**，症状式清理是**线性消耗**，永远追不上。
- **根治**：从"清存量"转成 **建契约堵增量 + 一次性全量核对清存量**。

---

## 3. 治理流程（5 步，按序执行）

### Step 1 — 定真实源（SSOT）

为要治理的每类数据，明确**唯一权威源**：

| 数据类型 | 真实源（权威） |
|---------|--------------|
| 字段/结构 | 后端 struct（能力层，字段上限）+ 客户端/前端真实表单（产品层，实际暴露子集） |
| 术语 | 术语规范文档 |
| 产品决策 | `decisions/` 的**实际状态**（不是某份旧"已收敛"文档） |
| 分级/枚举 | 后端枚举定义 |

> 两层真实源原则：**能力层**（后端能做什么）+ **产品层**（实际暴露什么）。前端字段必须在这两层有出处，否则是脏数据。

### Step 2 — 全量核对（不发现一个清一个）

对照真实源，**逐字段 / 逐词 / 逐功能**列出所有不一致。一次扫完，不等下次撞见。

```bash
# 假功能/占位
grep -rinE "mock|TODO|FIXME|placeholder|stub|fake|hardcode|dummy" <前端目录>
# 术语混乱（按项目术语替换关键词）
grep -rioE "<同义词1|同义词2|...>" <目录>
# 字段对照：前端 type 文件 vs 后端 struct，逐字段比对
```

并行用 Explore/Agent 分模块扫（创建表单 / 列表 / 过滤 / 详情各一路），汇总成清单。

### Step 3 — 分类（每项归一类 + 定处理）

| 类 | 处理 |
|----|------|
| 假 UI / 假字段 | **砍**（删前端 UI/字段） |
| 字段错配 | **对齐**（改名/改枚举/改类型到真实源） |
| 缺失（后端有前端无） | **按产品决定**（产品层暴露的才补，不照搬后端全字段） |
| 术语混乱 | **统一**（按术语规范替换，区分视觉符号/local 文案/内部代码三层） |
| 文档/知识库残留 | **删/改对**（直接清，不留"原来错的"记录） |

### Step 4 — 清理（直接改对，不留错误记录）

- 直接改对或删除，**不在文档里留"修正了什么错误"的记录节**（那是把错误内容又留回知识库，成新误导源）。
- 纠正过程要留痕 → 去 `decisions/` 或失误复盘，不在产品文档反复重述错误。
- 精确改：用 Edit 逐处替换，不重写整文件（避免丢内容/改坏结构）。

### Step 5 — 堵增量（建契约）

- **字段映射表**作为 SSOT：`前端字段 ↔ 后端字段(类型/枚举) ↔ 客户端字段 ↔ 状态`。新增前端字段前先登记真实源出处，溯不到 = 拒绝。
- **术语表**作为 SSOT：每个概念定唯一对外符号 + local 文案 + 内部代码词。
- 实现者以契约表为准，不自造字段/枚举/术语。

---

## 4. 分类决策树（快速判断一项是不是脏数据）

```
这个前端字段/UI/词 ——
  ├─ 真实源（后端/术语规范/decisions）里有出处吗？
  │   ├─ 没有 → 脏数据：假 UI / 残留 → 砍 or 删
  │   └─ 有 → 名/值/类型/用词一致吗？
  │       ├─ 不一致 → 脏数据：错配 / 术语混乱 → 对齐 / 统一
  │       └─ 一致 → 干净 ✓
  └─ 后端有但前端无 → 不一定补，看产品层是否暴露
```

---

## 5. 反模式（别这么做）

- ❌ **症状式清理**：发现一个清一个 → 永远清不完。要一次全量核对。
- ❌ **凭直觉造字段/术语**：不对齐真实源 → 制造新脏数据。
- ❌ **留错误记录**："修正了什么错误假设"节 → 错误内容又成误导源。
- ❌ **盲目 sed 替换术语**：不区分视觉符号/文案/代码三层语境 → 改出新错。
- ❌ **照搬后端全字段**：后端能力 ≠ 产品该暴露，以产品层（真实表单）为准。

---

## 6. 检查清单（治理一轮的 Done 标准）

- [ ] 每类数据的真实源已明确（SSOT）
- [ ] 对照真实源做了**全量**核对（不是抽查）
- [ ] 每项不一致已分类 + 定处理
- [ ] 清理直接改对/删，无"错误记录"残留
- [ ] 建了契约表（字段映射表 / 术语表）堵增量
- [ ] 纠正过程留痕到 decisions/ 或复盘（不在产品文档）

## 案例（示例 · MooX Web 2026-06-02）

- **发现**：角色创建表单 27 项与后端脱节（假 UI 3 / 错配 10 / 缺失 8 / 不持久 2）；分级术语 NSFW/R18/Mature 混用。
- **真实源**：后端 `CreateCharacterParam`（能力层）+ iOS 表单（产品层）+ 术语规范。
- **治理**：砍假分级；术语统一（视觉符号 / local 文案 / 代码词 / 内部保留四层分清）；建字段映射表随创建流落地。

> 相关：项目 `ai/principles.md` 的「对齐真实优先」「文档只呈现正确状态」「合理性思考」；姊妹 skill **decision-hygiene**（决策卫生，管决策层脏数据 + 触发时机）。脏数据治理是这几条原则在代码/数据层的执行。
