# 问题修复流水线

[English](./README.md) | [中文](./README.zh-CN.md)

把一批问题交给多个 AI agent 跑成队列驱动的闭环 —— 修完必须由另一个只读 agent 独立复验，再由人在看板上验收，才算完。

执行底座是 [Orca](https://orca.computer) 的 orchestration 原语。跨 agent 通用：Claude、Codex、Gemini 都能扮演任一角色。

## 问题出在哪

把一批 bug 丢给编码 agent，失败的方式很具体，而且不是大多数人预期的那种。

**它通常写得出那个修复。它做不到的是告诉你这个修复是不是真的。** 它会在从没运行过的代码上报告成功，会在只把文件编译通过时就把任务标记完成，而代价最大的那种 —— 它会把一个错误的问题正确地解决掉。

三种失败叠加：

- **自称绿灯。** 你拿到的唯一信号是 agent 说它干完了。这个信号和 bug 有没有消失之间没有相关性。
- **状态散落各处。** 终端输出、聊天记录、git status、问题看板 —— 四个地方，没有真源。agent 一重启，状态就没了。
- **并行 agent 互撞。** 两个 agent 在同一个 checkout 里改同一个文件，好一点是合并冲突，差一点是静默覆盖。

## 四个词

整套系统就是四个词，其余全是推论。

**队列是真源。** `orca orchestration task` 是唯一的机器可读状态。agent 之间的消息只是唤醒信号，丢一条不影响正确性；队列丢了就全乱。所有调度决策只读队列，从不读聊天记录。

**桶是隔离单元。** 一个桶 = 一组 touched-files 互不重叠的问题 + 一个 agent + 一个 git worktree。**桶数决定并发度，问题数不决定。** 桶间文件不重叠，并行合并就零冲突；桶内串行修，agent 能在一个模块上保有完整上下文。

**三证链。** 自证（修复 agent 说改完了）→ 他证（换一个**只读**的 agent 复验）→ 人证（人在看板上验收）。少一环就是假绿灯。他证必须换 agent —— 这条约束才是它成为证据而不是橡皮图章的原因。

**回边。** 复验不过、或者人打回 → 问题作为新任务重新入队。这条边让它成为循环而不是流水线。

## 五个角色

每个角色只读自己那一份，没有人读整本手册。

| 角色 | 干什么 | 文件 |
|---|---|---|
| **intake** | 人机界面。接问题、查重、写队列和看板 issue | [`roles/intake.md`](./roles/intake.md) |
| **analyzer** | 按 touched-files 把问题聚成桶、建任务链、起 worker 派活 | [`roles/analyzer.md`](./roles/analyzer.md) |
| **fixer** | 桶内串行修复，跑自证小循环，一个问题一个 commit | [`roles/fixer.md`](./roles/fixer.md) |
| **verifier** | 派他证、请人验收、落地合并、销毁桶 | [`roles/verifier.md`](./roles/verifier.md) |
| **watchdog** | 其余角色的存活探针 + 按队列重放 | [`roles/watchdog.md`](./roles/watchdog.md) |

第六个终端 [`console`](./roles/console.md) 纯粹是人的接口和手册维护者 —— 它不是流水线角色，不承担任何队列职责。

## 一条问题走完全程

```
你报一个 bug
  → intake      查重 → 建看板 issue → 建 task（ready）
  → analyzer    分桶 → 建 fix task + verify task（依赖 fix）→ 起 agent → 派活
  → fixer       改 → 自证（编译/测试）→ commit 到桶分支 → worker_done
  → verifier    起一个不同的只读 agent 复验 → PASS → 落地：
                先落状态 → rebase → 编译 → 报告进库 → 合回 → 销毁桶
  → 你          issue 停在 Review；拖 Done 放行，拖 Todo 打回
```

落地那一步的顺序是有讲究的。**状态必须在销毁桶之前写完** —— worktree 一没，就没地方写了。而**合并发生在他证 PASS 之后、人证之前**，这样人是在自己的分支上验收，而不是切到一个即将被删的桶里。代价是人证打回需要 revert。

## 真实的账

这一节是这份文档存在的理由。上面那些设计写下来很容易，下面是真跑出来的东西。

**一个 bug 跑了三轮，两次返工都不是修得不好：**

- **第 1 轮 —— 人证打回，方向错了。** 我写的 spec 要求改成非阻塞的 toast 提示。而产品需求文档明确要求的是阻塞式错误态加重试。他证判了 PASS —— 因为它把一个错误的需求正确地验证了。全部回退。
- **第 2 轮 —— 他证 FAIL，判据写错了。** 我把一个基线上早就存在的缺陷写进了这个 issue 的验收判据。修复本身合格，判据不合格。verifier 忠实执行判据，判掉了一个正确的修复。那个缺陷被拆成独立 issue —— 这次返工直接催生了手册里的第 10 条纪律。
- **第 3 轮 —— 通过，落地。** 那时自证质量明显上来了：实跑 5 条真实交互路径 + 56 条回归测试 + 编译通过。

**两次返工都是入口质量问题，不是产出质量问题。** 手册里那些规则不是设计出来的，是这两轮返工的账单。

**还有一笔更难看见的账**：这次会话有一段时间，五个 agent 在互相讨论方法论，而流水线的实际进度是零。是 watchdog 先注意到并主动把自己收回到只做存活检查。**任何允许 agent 互相对话的系统，都需要有人被授权说一句「我们在产出洞察，但没有产出」。**

## 跑出来的失败模式

这些都是撞上去才发现的，而且每一条都**静默** —— 不报错、不抛异常、退出码为零。

| 故障 | 表现 | 你会得出的结论 |
|---|---|---|
| 收不到 | 阻塞等待返回空，不报错 | 「队列很闲」 |
| 发不出 | 发给一个已不存在的地址，仍返回 `ok: true` | 「消息已送达」 |
| 查不出 | 拿发送的返回值当存活证据 —— 它**恒真** | 「对方还活着」 |
| 内容坏 | 消息正文经过 shell，反引号被执行、`$` 被展开 | 「发出去的是我写的那段」 |

共同点不是寻址方式，而是 **命令的返回值报告的是「这条命令被受理了」，不是「你想要的效果发生了」**。对每个新命令都先这么假设，直到证明不是。

另外两条，属于值得单独命名的一类：

**会理直气壮撒谎的监控。** 一次探针改造在上线前先做了干跑，结果发现它匹配到零个终端 —— 一个常量被写成了选择器格式，而数据字段里没有那个前缀。要是直接上线，它第一轮就会宣布七个 agent 全部死亡，而一个行为正确的 watchdog 会照着把六个活着的重启一遍。其他静默失败导致的是**漏动作**，坏掉的监控导致的是**错动作**。任何会对世界下判断的东西，改完先干跑。

**「我用过」不等于「这里能用」。** 手册里曾经写着一个不存在的解药：一个 `--body-file` 参数，被写成了「正文被 shell 吃掉」的对策。那个参数是真的 —— 只是在同一个 CLI 的**另一个子命令**上，而且在那里被成功用过十几次。**从真实经验里错误泛化，比凭空编造更难查**，因为写的人手上有真实的成功做背书，重读一遍也只会想起「我用过啊」然后跳过。它一直活到有人真去敲了一次。**经验的适用边界，要和经验本身一起记下来。**

## 哪些还没被证明

直说，因为一份只列成功的案例记录不构成任何证据：

- **多桶并行从没跑过。** 桶隔离的存在意义就是并发，而目前每次会话都是单桶串行。**这个设计的核心主张是未经验证的。**
- **人验收后的自动唤醒未经实测。** 设计上靠 watchdog 探针发现看板状态变化，没有人真的看着它发生过。
- **空闲时的行为是浪费的。** 队列为空时常驻角色阻塞等待，超时唤醒一次、重新推导一遍「什么都没变」。

## 怎么用

把 [`SKILL.md`](./SKILL.md) 和 [`roles/`](./roles/) 放进你的 agent skill 目录，在项目 worktree 里开一个 agent，说一句「启动 fix pipeline」。`SKILL.md` 的启动章节会接管剩下的事 —— 建控制面、起角色终端、装 watchdog 定时任务。**不需要脚本，手册本身就是脚本。**

这份手册是写给 agent 读的，不是写给人读的。它很密，在重复能防住某个具体错误的地方它就重复，而且几乎每一条规则后面都跟着催生它的那次事故。
