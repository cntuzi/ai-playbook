# Conversation Ledger 的 Token 开销评估

日期：2026-09-16。评估实现：`604b9a8`。

## 结论

自动落盘不调用模型，问题整理会增加模型输入、输出和工具调用。当前版本每次用户发言都提示主 Agent 整理待处理来源，因此不应把它描述为“几乎零成本的记录工具”。

对两条短消息、更新一个简短问题的情景，预算可先按每次整理额外 **2,000–4,000 输入 token、600–1,500 输出 token** 估计。首次加载规则另约 4,400 输入 token。这是文本规模与流程估算，不是宿主实际 usage 的 A/B 测量；不包含新增推理 token、后续请求再次携带历史的输入，以及额外工具调用对原有长上下文的重传。复杂讨论和积压批次可能显著超出该范围。

## 测量口径

- 对实际安装代码生成的提示、Skill 文件、模拟 `review` 返回和样例笔记，用 `tiktoken` 的 `o200k_base` 编码计数。
- `o200k_base` 仅作为可复现的长度代理，不代表 Codex 当前模型或 Claude/Pi 所选模型的精确计费分词器。
- 在临时目录调用本地采集与整理 CLI 生成样例，没有请求模型推理，也没有给真实队列加入模拟记录。
- 示例包含 64 个字符的中文用户消息和 143 个字符的助手回复，正文合计 125 个代理 token；实际路径、UUID 和宿主包装会改变计数。
- 尚未取得开启与关闭 Ledger 的真实输入、缓存、输出、推理和模型调用次数对照数据。不能据此承诺固定百分比或费用。

## 已计数的组成

| 组成 | 代理 Token 数 | 出现时机 |
| --- | ---: | --- |
| 本地采集 JSON、导出 Markdown | 0 个模型 token | 本地代码运行；不经模型生成 |
| 实际 `context()` 提示 | 383 | Codex/Claude 的 SessionStart 和每次 UserPromptSubmit；Pi 的 before_agent_start |
| `SKILL.md` | 1,318 | Agent 首次读取，或上下文压缩后需要重新读取 |
| `references/runtime.md` | 1,557 | 读取采集与 review/ack 规则 |
| `references/storage.md` | 1,499 | 读取记录布局与状态更新规则 |
| 三份规则合计 | 4,374 | 全部首次读取时的文本输入规模 |
| 两条短消息的 `review` JSON 返回 | 985 | 模型调用 review 工具后读取 |
| 同一返回中将正文清空后 | 860 | 说明 IDs、路径、字段和规则提示占了较大部分 |
| 两事件的样例 review 回执 | 265 | 模型生成写入内容；回读时又成为输入 |
| 一个现有简短问题笔记 | 344 | 读取或生成该规模内容；回读另算输入 |

样例问题和回执合计 609 token，只表示正文规模。工具调用封装、路径参数、额外总结与推理不包含在这 609 token 内。规则正文通常不必每轮重新读取，但只要仍在历史上下文中，仍可能在后续请求中计入输入。

安装三个宿主接入不会让一个宿主的对话自动调用三次模型。五个生命周期 Hooks 也不是五次模型调用；当前 command hooks 没有模型 API 调用，Stop 不强制开启另一轮。

## 20 轮讨论的估算

这里一轮表示用户发言及 Agent 完成回应；一轮可能包含多次模型请求和工具调用。

### 只看提示注入

在 Codex/Claude 一次 SessionStart 加 20 次用户发言的前提下，新增提示文本约为：

`383 × 21 = 8,043 token`

这是新增提示文本量，不是累计模型输入。如果每轮保留之前全部提示、没有压缩，并简化为每轮只请求一次模型，则这些提示在 20 次请求中的累计输入约为：

`383 × (20 + 1 + 2 + … + 20) = 88,090 token`

这是说明历史重传的假设示例，不是实际会话预测。宿主上下文管理、缓存和同轮工具调用都会改变结果。

### 每轮完成一次小型整理

假设每次处理约两条消息，读取相关问题，写一个简短更新与回执，再回读确认；不积压更多事件：

- 20 次整理的各环节首次输入规模，连同首次规则读取，约 **4.4–8.4 万 token**。
- 新生成的文本与工具参数约 **1.2–3 万输出 token**。
- 上述输入范围包含每轮提示；不重复加上一节的 8,043。
- 后续重传与推理另计；增加工具步骤还可能让原本的任务上下文多进入模型几次。

因此即使笔记很短，轻量聊天中的相对增幅也可能较大。在长上下文、多工具调用的开发任务里，单次注入占比可能较小，但实际增幅依然取决于新增模型请求数。没有同任务基线，不能给出可信的“增加 5%/10%”结论。

## 缓存与账单

缓存可能降低重复输入的价格，但不等于重复输入从 usage 或上下文中消失。不同模型的缓存读写规则不同，应分别记录输入、缓存读取、缓存写入与输出，而不是将全部 token 乘同一价格。[OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)

如果使用订阅中的 Agent 额度，API 美元价格也不能直接等同于该订阅额度的消耗。

## 建议的下一版

1. **继续逐事件自动采集，降低整理频率。** 本地计数达到阈值、用户要求保存或准备压缩时再提示整理；结束时无法运行模型就保留待整理状态。
2. **缩短每轮注入。** 将长路径与固定说明移出每轮提示，以少量状态和入口替代。目标可先定为 100 token 以内，需验证宿主仍能正确找到操作规则。
3. **减少 review 元数据。** 返回必要的事件身份、来源和增量正文；不要把内部完整事件对象逐条重复交给模型。保留证据关联与正确确认批次的能力。
4. **合并本地机械步骤。** 用工具完成模板渲染、回执生成与一致性检查，让模型主要输出问题变更，减少逐文件生成和回读。
5. **先评估批处理，再决定独立 Advisor。** 每 5 轮整理一次，可把 20 次固定流程触发降为 4 次；原始内容仍需处理，所以总 token 不会必然减少 80%。单独的小模型可以降低费用，但多了一次观察者推理，不天然降低总 token。

以上为设计建议，当前发布版尚未提供这些低频整理开关。

## 如何取得真实增幅

用相同固定脚本进行关闭 Ledger、当前逐轮整理、未来批量整理三组测试。每组包含主题切换、明确搁置、用户纠正、跨会话续聊；保持宿主、模型和推理配置一致，重复运行以估计波动。

记录模型调用数、输入、缓存读写、输出/推理明细、延迟，以及保留下来的问题是否正确。输入和输出应分别比较增幅；费用按实际模型规则计算。成本与问题保留效果同时达标，才能选择默认模式。
